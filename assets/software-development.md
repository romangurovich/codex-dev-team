# Software development

Apply this workflow when implementing, fixing, refactoring, or reviewing software in any project. Repository and path-specific instructions supply the project's architecture, conventions, commands, and required checks. Read them before acting; keep this shared workflow independent of any stack. Scale investigation and verification to the affected behavior and risk while satisfying explicit project requirements.

1. **Define acceptance criteria.** Translate the request into observable outcomes, affected users or callers, and relevant failure cases. For a bug, identify the trigger and expected behavior; for a refactor, identify behavior that must remain equivalent. Resolve consequential ambiguity before dependent implementation, and continue independent discovery. **Complete when:** each requested outcome has a concrete way to verify it, and necessary assumptions are explicit.

2. **Establish the baseline.** Inspect the current branch, working tree, existing changes, applicable instructions, and nearby implementations. Identify module boundaries, callers, external dependencies, generated files, and relevant documentation. Preserve unrelated work; arrange isolation when simultaneous edits or builds could collide. Record pre-existing failures separately from regressions introduced by the task. **Complete when:** the intended diff and ownership are clear, and implementation follows validated local patterns or explains a necessary departure.

3. **Discover the real checks.** Read package/task scripts, test-runner configuration, workspace membership, CI, and relevant test files. Identify filters, excluded directories, separate integration or snapshot suites, optional services, credentials, and conditions that skip tests. Use the project's runtime versions, package manager, lockfile, and reproducible installation method. Confirm that aggregate commands actually include every affected package and behavior. **Complete when:** there is an executable verification plan covering acceptance criteria and required gates, with setup needs and coverage gaps identified.

4. **Implement with focused behavioral evidence.** Make the smallest coherent change. Add or adapt a narrow regression test where it protects meaningful behavior; demonstrate that it detects the original bug when practical. For trivial documentation or configuration edits, use appropriate validation instead of redundant tests. Exercise real implementation and mock external boundaries, such as network responses or SDK transport, rather than the behavior under test. Isolate database, filesystem, process, and global state; control clocks and await observable events or conditions instead of fixed sleeps. Model meaningful domain states explicitly, including absent, invalid, and failed results when they differ. Use synthetic fixtures that exercise meaningful branches and boundaries; redact customer PII from shared or committed evidence and keep authorized local diagnostics in the project's ignored location. Update generated outputs through their canonical generator and inspect the diff for reproducibility. **Complete when:** the change satisfies its focused checks, introduced dependencies are justified, and generated outputs agree with their sources.

5. **Verify the affected runtime.** For UI changes, exercise representative affected journeys in a real browser or native runtime, including relevant loading, empty, error, permission, theme, and viewport states. Inspect appearance, interaction, console errors, and failed requests. Use a production build when behavior depends on bundling, deployment headers, assets, workers, or host embedding. For backend or library changes, exercise relevant integration boundaries and caller contracts. Establish provenance: the server, bundle, artifact, fixture, or benchmark must correspond to the current source, configuration, and inputs. A historical PASS or stale running server is insufficient. **Complete when:** runtime evidence covers the affected acceptance criteria and its source is identifiable; any unavailable checks are explicitly recorded.

6. **Integrate and independently review.** Combine all changes before final verification. Run the discovered required gates and relevant integration checks against the final integrated source. For nontrivial changes, use an independent reviewer along two axes: compliance with applicable project standards, and fulfillment of the request and acceptance criteria. Inspect the actual diff, callers, tests, and runtime evidence; prioritize concrete correctness, security, compatibility, and regression findings. **Complete when:** required gates pass, passed/skipped/failed checks are distinguished, and material review findings are resolved. If essential evidence is unavailable or a material finding remains, continue useful work and report a partial or unverified result rather than claiming completion.

7. **Repair and close.** After repairs, rerun affected checks and any gates whose earlier result the change invalidated. Broaden testing for a new failure or unresolved concern; stop arbitrary repetition once adequate checks pass. Report the resulting behavior, important changes, exact validation performed, and remaining limitations or unverified environments. Follow the repository's PR template and mark checks complete only when actually performed. Software-development authorization alone does not authorize deployment, publishing, merging, or other external release actions; use the user's explicit scope. **Complete when:** the final diff and evidence are reviewable, requested work is accounted for, and the user can distinguish verified outcomes from limitations.
